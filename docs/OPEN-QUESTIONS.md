# Open questions

Everything the chapters could not settle from the restore image, kernel, firmware, dyld cache and public sources, collected from each chapter's gaps/limits sections (generated by `tools/gen_gaps.py`). This is the research agenda for anyone with a real device, a different build or more time.

213 open items across the chapters.

## [00: Method and evidence](00-method-and-evidence.md)

### [Limits](00-method-and-evidence.md#limits)

- **No silicon-level data.** Transistor counts, gate layouts, cell libraries and netlists are not in any of these sources. Neither are board schematics or the register-level programming model of Apple's blocks. The deepest this map goes is the boundary Apple itself draws in the device tree: a block, its MMIO window, its interrupt lines, and the driver that owns it.
- **Encrypted firmware.** SEP is encrypted, and so are parts of the cellular and other firmware. Chapters say when a payload could not be read.
- **One build, one variant.** Everything is observed for iOS 27.2 24B91020 on V68AP. Addresses and offsets are observations of this build, not constants.
- **No device on the bench.** Nothing here comes from probing real hardware. The only runtime evidence is from the vphone-duo VM, which differs from a real Duo, most notably by having one display instead of two.


## [01: The SoC, CPU, memory and storage fabric (t8160 / A20 Pro)](01-soc-cpu-memory-storage.md)

### [16. Gaps and limits](01-soc-cpu-memory-storage.md#16-gaps-and-limits)

- **The runtime memory map, DRAM size and DRAM vendor are unknowable from the IPSW.** iBoot fills `/memory`, `/chosen/memory-map`, `/chosen/carveout-memory-map`, `dram-vendor`, `/vram`, `/pram` and the CTRR lock regions at boot. All are zero here. Reading them needs a live device tree (`ioreg -p IODeviceTree` on hardware). `device-perf-memory-class 12` is a hint, not a size.
- **CPU frequencies, voltages and P-state tables are not in the tree.** CLPC's frequency-like scalars (4500, 2412, 1116) have no unit in the tree. The MHz reading is my inference.
- **Which bin overlay applies.** The tree carries both `h19p` and `h19a`. That this device uses `h19p` is inferred from the public "A20 Pro" name and the dual-ANE (`ANE1`) content.
- **L1 cache sizes, core microarchitecture and which `FEAT_*` features are actually implemented** are runtime values (sysctl). They are not in these files.
- **Which ANS controller class binds** (ANS2 vs ANS3 variants) is decided in `probe()` at runtime.
- **NAND facts are not here:** vendor, process, die count, capacity, the meaning of the `namespaces` triples, and the MSP firmware contents. `t303.aus5` and the MSP firmware are not separate files in this IPSW.
- **PMC and MSR firmware** have no readable strings, so their internals are opaque beyond the kernel's view of them.
- **Register-level semantics.** Offsets such as `cluster-ctl-offset` and the AIC strides are given by Apple in the tree. What the bits inside those registers do is not public, and I did not invent any.
- **The dyld shared cache was deleted at about 20:04, partway through this work (not by this chapter's author), and was not re-extracted to save disk space.** Userland evidence in this chapter is therefore limited to the image list captured before then (`ipsw dyld info -l`: `IOKit`, `libIOReport`, `PerformanceControlKit`, `AppleNVMe`, `NANDInfo`, `APFS`, `MobileStorage`, `PowerLog*`, `kperf`, `ProcessorTrace`, `libMobileGestalt`, …), plus kernel strings and public API docs. I did not inspect the ObjC classes or symbols inside those images.
- **The SPTM/TXM boot and attestation flow** is out of scope here (security chapter). Only their memory and DMA policing is described.
- **No schematics, die photos or transistor-level data** exist in any source used here.


## [02: Boot and security](02-boot-and-security.md)

### [20. Gaps and limits](02-boot-and-security.md#20-gaps-and-limits)

- **SecureROM and SEP Boot ROM.** These are mask ROM. Their code, the exact fuse map, and which core they start on are not in the IPSW. The step order in [§1](#1-the-cold-boot-step-by-step) follows Apple's public description plus string evidence.
- **SEP OS and SepStage1.** Both are encrypted with GID-wrapped KBAGs. Endpoint names come from the kernel only, and nothing inside SEP OS (applets, matching algorithm, key hierarchy) is observable here.
- **Secure Element and eUICC.** Their OS and applets are opaque.
- **Exception levels.** Where SPTM, TXM and cL4 run (privilege level and "guarded" mode) is inferred, not shown. iBoot's exact jump target is also inferred.
- **`/chosen` values.** The IPSW device tree is a template. Real values such as the ECID, the nonce, effective production status and the `boot-manifest-hash` exist only on a live device.
- **Undecoded fields.** Device-tree `reg` values are pre-translation (relative to `/arm-io` ranges). The Mesa `reg` layout, the GPIO interrupt flag word, and the function fourccs (`pKW8`, `pcLD`, `keyR`, `pmOC`…) are not decoded. Their semantics are Apple-internal.
- **iBootData** contents are not identified.
- **Userland side.**
  - The dyld shared cache was deleted at about 20:04, partway through this research, and was not re-extracted.
  - **[DSC]** claims here are limited to the image list, the BiometricKit ObjC dump, and a few string hits for `com.apple.biometrickitd` gathered before the deletion.
  - Daemon binaries (`biometrickitd`, `nfcd`, `seld`, `securityd`, `keybagd`, `coreauthd`, `amfid`, `cryptexd`) are not in the shared cache. Their exact mach-service names, other than biometrickitd, were not verified.
- **The Apple Pay, data-protection-class and Touch ID pairing flows** follow Apple's public Platform Security guide (<https://support.apple.com/guide/security/welcome/web>). These sources do not show them.
- **Hardware below the device tree.** No register specifications, no schematics, and no information on how the side-button sensor connects across the hinge.


## [03: GPU and displays](03-gpu-and-displays.md)

### [9. Gaps and limits](03-gpu-and-displays.md#9-gaps-and-limits)

- **No register-level knowledge.** The `reg` windows and IRQ numbers are known; what is inside them is not. That covers GPU, DCP and pipe register maps, the scaler programming model, and the TCON command set. Nothing here invents them.
- **GPU shader-core count, clocks and perf-state table.** Not in the restore device tree: `perf-states` is 0, filled by iBoot per device. `gpu-num-perf-states = 2` is as found and is likely not the whole DVFS table. The 7-core figure is [PUB] only.
- **Neural Accelerators.** The evidence is the Metal 4 ML encoder and tensor classes in `AGXMetalG19P`. How the hardware implements them is not visible.
- **Panel link.** "MIPI" and "ALPDP" both appear (`secure-mipi`, `mipiLaneCount`, `alpdp…` failsafe categories). Which one each panel uses, the lane count and the link rate are not stated.
- **No panel timing, TE or vsync GPIO in the DT read.** These live in the panel EEPROM and DCP firmware, not in readable form. Refresh-rate ranges (1–120 Hz) are [PUB] plus firmware string names only.
- **Panel suppliers and driver ICs.** Not named in any source. `brightness-secondary-doe1` hints at two inner-panel configurations.
- **The 2007 × 2853 canvas.** That it is the 460-dpi re-expression of the 1878 × 2670 panel, scaled down by the pipe, is an inference from consistent numbers and CA/IOMFB symbols. The scaler stage that does it was not seen in code.
- **ASC interrupt numbers** for `dcp`, `dcpsec` and `dcpext0` were not decodable from the dump.
- **DCPSEC firmware-service matching.** No prelinked personality names role `DCPSEC`, so how its `AFKFirmwareService` attaches is unresolved.
- **"RDLC", "ACSS", "ALSS", "APT", "PDC", "BIM".** Only the abbreviations appear. The expansions given are [INF].
- **Exclave internals.** `EXDisplayPipe`, `EXBrightCore` and `DisplayHealthMonitor` run in exclaves whose code is in `exclavecore_bundle.v68.RELEASE.im4p`, which was not analysed here (see [02-boot-and-security.md](02-boot-and-security.md)). Only their XNU-side proxies and DT contracts are described.
- **Userland after the cache was deleted.** The dyld shared cache used for this chapter was deleted from the shared scratch area during the work. The [DSC] facts here were gathered before that:
  - `AGXMetalG19P` ObjC classes;
  - `IOMobileFramebuffer` exports;
  - QuartzCore canvas and flipbook strings;
  - `AppleEmbeddedDisplayServices` BIM strings;
  - the image list.
  The SpringBoard pose, policy and `_UISceneHingeStateHostComponent` facts come from vphone-duo's earlier extraction of the same 27.2 cache. These were not re-read:
  - the full backboardd and FrontBoard display arbitration code;
  - `CoreBrightness`'s use of the `/core-brightness` tables;
  - which public UIKit API surfaces the hinge angle.
- **Runtime.** Nothing was observed on a real Duo. The only runtime data is vphone-duo's single-display VM, which cannot present both panels.


## [04: Camera, media and the Neural Engine](04-camera-media-neural-engine.md)

### [10. Gaps and limits](04-camera-media-neural-engine.md#10-gaps-and-limits)

- **No sensor-level wiring.** The device tree has no sensor nodes. The I²C bus and address, SPMI lane, LPDP/MIPI PHY port and lane map for each camera are held in binary tables (`CConnectivityTableV68`, `vcList`) inside `adc-boreas-v68`, which this chapter did not decode. The sensor-to-camera mapping in §3.3.2 is an **inference** from which drivers have Secure-M3 variants and from V68-specific strings, not a read of the board table.
- **The Secure M3's location.** There is no device-tree node and no MMIO; its interface is known only from firmware strings. Which bus it masters, and whether it sits in the camera module, on the logic board, or in the SoC, cannot be determined.
- **The strobe IC.** Five strobe driver classes exist (Antlia, CP5100, Quark, Regulus, Rigel). Which one V68 uses is not recoverable from strings.
- **The Camera Control button.** Only the device-tree flag, its location and the SMC `capture` button event are visible. The force and capacitive sensing path, its firmware and the HID descriptors are not established here.
- **Yonkers and the `Glenbrook`/`Lakeville` patches.** These are signed, per-module patch blobs whose consumer is unknown.
- **The exclave internals.** `ISPEngine`, `ANEExclave` and the indicator controller run inside the encrypted or opaque exclave bundle (`exclavecore_bundle.v68.RELEASE.im4p`). What exactly the CIL breaker checks is inferred from strings, not observed. See [02-boot-and-security.md](02-boot-and-security.md).
- **Neural-core counts and ANE microarchitecture.** "Dual 16-core" is the public figure. Neither the device tree nor the firmware strings enumerate the cores. `ane-type 0x400` is not decoded.
- **The RISC-V AVE slices.** The ISA is established from the Mach-O CPU type and the instruction encoding. What each of the nine slices does is not known.
- **The ProRes engine.** pmgr has a `PRORES` power state and HW ProRes plug-ins exist, but no kernel node or kext was found. How it is reached is unknown.
- **Userland internals.** The dyld shared cache was deleted mid-research, so only image *paths* are cited. Executables outside the cache (`cameracaptured`, `mediaserverd`, `aned`, `assetsd`) were not examined. The objc class and symbol flows in §9 are **[INF]**, based on public API roles and kernel-side strings.
- **Below the block boundary.** Register-level programming models, ISP pipeline stage internals, sensor register maps (beyond names) and silicon layouts are not public. Nothing here goes below the MMIO window and interrupt line the device tree gives.


## [05 · Sensors, touch, buttons, audio and haptics](05-sensors-touch-audio-haptics.md)

### [Gaps and limits](05-sensors-touch-audio-haptics.md#gaps-and-limits)

- **Dyld shared cache.** It was deleted mid-task and deliberately not re-extracted. The following need the cache (or a device) to verify: which framework exports which hinge symbol beyond `CLAngleNotifier` → CoreMotion; whether `CMAngleManager` and `UIHinge` are public SDK API; the exact backboardd → UIKit touch routing code; the audio daemon chain (mediaserverd/audiomxd/HAL plug-ins); haptics daemons; and which process hosts the SensingAlgs frameworks.
- **Physical buses of AOP sensors.** The IMUs, magnetometers, barometer, ALS, prox and Hall sensor are DT children of the AOP nub with no bus or address information visible to the AP. Part numbers (except where a kext names a family: CT7xx, VD628x for ALS; Atlantis for prox; CS42L79 and CS35L28 for audio) are not in the evidence.
- **Hinge HID usages.** Three usages appear (0xFF0C/0x1C Crane, 0xFF0C/0x21 per the prior research, 0x20/0xE4 standard hinge angle). Which service a real Duo publishes, and the exact report layout, needs a live `ioreg`/`hidutil` dump.
- **Where the Hall-effect closure sensor is.** It is in the firmware strings only. Its location and magnet are unknown.
- **SMC firmware.** `t8160smc` has no separate BuildManifest component, and I could not identify its source. It may be part of another image.
- **`aon-ptd`.** Its acronym and register semantics are not public. Only its role as a co-processor-written table with AP interrupts is inferred.
- **Touch ASIC internals.** "cypher2" is Cortex-M (armv7em) by the firmware config. Electrode counts, AFE design and the meaning of DTN/Cantor/Fermat parameters are not public.
- **Camera Control = `nova`/Mando** is an inference from matching tags. Nothing in the evidence spells "Camera Control".
- **"action" button.** It is a PMU event name only. Whether the Duo has a physical Action button is not established.
- **Four ALS.** The tree shows three display ALS. A fourth exists only if the `grimaldi` photon detector is counted.
- **Speaker naming** (`arc` vs `btmspk` → which grille) and whether "arc" relates to `AppleHapticsSupportArcEEPROM` (no matching DT node) are unknown.
- **Interrupt encoding** of the IOP nodes (`r`,`s`,`t`,`u`) is shown raw. I did not verify it as numeric IRQ lines.
- **Not knowable from these sources:** schematics, transistor-level design, register maps of AOP/MTP/LEAP/ADMAC, and Apple-internal sensor-fusion algorithms beyond what log strings reveal.


## [06 — Power, batteries, charging and thermal](06-power-battery-thermal.md)

### [13. Gaps and limits](06-power-battery-thermal.md#13-gaps-and-limits)

- **SMC firmware** `t8160smc` (DT `firmware-name`, `pre-loaded = 0`) is not present under that name in the IPSW, the BuildManifest, the kernelcache or iBoot strings that I checked. Its location (embedded compressed in another image, or in a component I did not decompress) is unresolved. So the SMC key map (which keys carry pack, charger and rebalance data) is not recoverable here. The kernel log formats print keys as `%c%c%c%c`, so the names are runtime-only.
- **Charger and gauge physical buses:** behind the SMC, so not in the AP device tree. Chip vendors and part numbers for the charger(s), gauges, BPIC (`stonehenge`), `shamisen`, PMUs (`becketts`, `fairmont`) and port controller (`cbtl1702`) are Apple code names only.
- **Rail map:** the DT gives SoC rails (DCS/SOC/DISP/AVE plus CPU/GPU domains) and PMU fault names for some LDOs and bucks. It gives no voltages, current limits, or buck-to-rail assignments. Those live in PMU firmware (inside iBoot) and Apple-internal schematics.
- **Hinge power path:** which conductors cross the hinge (VBUS vs VBAT bus vs flex) is not knowable from software. Teardown photos are the only source.
- **Units:** many CLPC and PPM constants are fixed-point. I give raw values and do not convert, except where noted as **[INF]**.
- **Userland daemons** (`powerd`, `thermalmonitord`, `batteryintelligenced`, `peakpowermanagerd`) are outside the shared cache. Their logic is not analysed here. The shared cache was deleted mid-session, so the [DSC] facts here are limited to the image list, the `BatteryPackCount` hits (PowerlogCore, PowerlogLiteOperators, PowerlogHelperdOperators, `-[PLBatteryAgent setBatteryPackCount:]`) and raw subcache byte matches. Which framework consumes `RebalanceData`/`IPDRatio`, how BatteryCenter shows one merged percentage for two packs, and how Low Power Mode maps to CLPC `pkg-lpm-power-target` are not determined.
- **SoC bin:** whether this unit uses the `h19p` or `h19a` thermal tables is decided by iBoot at boot and is not in the static DT.
- **Two "B" CLPC targets** (`pkg-sustainable-power-target-B`, `pkg-lpm-power-target-B`): the selection condition is not stated.
- Nothing here is register-level. No PMU register addresses beyond those the DT itself exposes are given or implied.


## [07: Networking and connectivity](07-networking-and-connectivity.md)

### [13. Gaps and limits](07-networking-and-connectivity.md#13-gaps-and-limits)

- **DSC loss.** After the deletion, these userland facts could not be verified: daemon executables, Mach service names, ObjC classes of CoreTelephony / IO80211 / CoreWiFi / Network.framework, and launchd plists. Daemon names in this chapter are [INF/PUB].
- **DriverKit dexts.** *(Corrected by [chapter 11](11-userland-radios-power-sensors.md): the `AppleCentauriAlpha`, `Beta` and `Control` dexts are in the restore ramdisk, cataloged in [`reference/ramdisk/`](../reference/ramdisk/README.md). Wi-Fi publishes six `IOUserNetworkWLAN` interfaces (STA, AWDL, LowLatency, SoftAP, NAN, NAN-data) and Bluetooth runs over shared-memory PCIe rings, not UART. Their WLAN/HCI code proper is not in the ramdisk.)*
- **Encrypted or opaque firmware.**
  - The Stockholm SE payload and eUICC (vinyl) images are opaque beyond their headers.
  - The C2 `CR`/`P`/`R`/`FR` blobs have no readable strings that name their purpose. The interpretations of `FR20`/`R2xx` and of the per-SKU sets are inferences.
- **Section → manifest key mapping** for the ftabs is inferred from names and sizes. The ftab itself does not store the `Wireless1,*` / `Cellular1,*` key.
- **Wi-Fi 7 specifics.** No MLO, EHT, 320 MHz or 4096-QAM strings survive in the stripped N1 cores, so the Wi-Fi 7 feature set rests on [PUB].
- **mmWave hardware.** No device-tree node exists for antenna modules, and no RFFE/MIPI-RFFE bus is visible to the AP: the RF front ends are controlled by the modem. Module count and placement in the folding chassis are unknown.
- **GNSS.** The relationship between the C2 `GNS0` path and the AOP `GNSS ... SPI driver` code path is unresolved. Constellations and bands are not enumerated in strings.
- **Physical layer.** Lane counts, PCIe Gen negotiated at runtime, register-level behaviour of the SPMI billboards, the meaning of "HEB", and every schematic, antenna and RF-front-end part number are not public.
- **One build only.** Offsets, versions and pipe numbers are observations of iOS 27.2 24B91020.
Related chapters: `00-method-and-evidence.md`. The display chapter covers the DCP/DisplayPort path past the crossbar. The power chapter covers MagSafe (`WirelessPower.v68.im4p`) and the SPMI PMUs.


## [08 — The foldable as a system, and the chassis](08-foldable-system-and-chassis.md)

### [9. Gaps and limits](08-foldable-system-and-chassis.md#9-gaps-and-limits)

- **No schematics, flex pinouts or board layout.** Which half holds the logic board, the two
  batteries, the second PMU, the second NFC controller and the second IMU is not in the DT. The hinge
  flex has no device-tree presence. iFixit's single-board and single-flex description is the only
  physical evidence.
- **Hinge mechanics.** Apple publishes only the 3D-printed titanium cover. The 100+ part count,
  Liquidmetal, aluminium and fibre-plate claims, and closure magnets come from secondary or leak
  sources. iFixit's crack theory is explicitly unconfirmed.
- **The AOP sensor buses** (IMUs, HES, compass) are owned by AOP firmware. There are no reg or IRQ
  entries for those sensors in the DT, so their bus type (SPI/I²C/I3C) and addresses are unknown.
  Register-level behaviour of the estimator is not knowable from strings.
- **Usage 0x21 vs 0x1C.** This chapter shows 0x1C from the kernel personality and takes 0x21 from
  the vphone research. Which usage carries the production angle events on hardware is
  **[INF]**.
- **Native public API.** After the cache was deleted, UIKitCore and SwiftUI could not be dumped. The
  absence of a public hinge or posture API is unproven. The WebKit Device Posture API is the only
  public, app-reachable posture API confirmed.
  *(Resolved in [chapter 10](10-userland-display-fold-touch.md): public `UIHinge` / `UIHingeInteraction`, iOS 27.1+.)*
- **DCP use of the angle.** The override properties prove the DCP stack carries a hinge angle. What it
  does with it (panel power, crease compensation, refresh) is not visible in these sources.
- **The 2007 × 2853 canvas** is interpreted as a downsampled render canvas. That is an inference, not
  confirmed against a real device's `UIScreen` values.
- **Image attribution** of the [DSC] class names relies on name prefixes. The extraction did not
  record image paths.

## [13: Lifecycle: the Duo as software sees it, from factory to erase](13-lifecycle.md)

### [9. Gaps](13-lifecycle.md#9-gaps)

- **Factory tooling is not in the IPSW.** The station software, the syscfg writer and the FDR upload client are absent. The factory stage is reconstructed from what restore *reads back* (the sealing map, syscfg pointers and the astris boosters). Which Duo chips, if any, are SWD-flashed is unknown.
- **Values are absent.** The IPSW device tree is a template, so no real calibration, `RCHL` or `rpcp` value is visible. The format of `RCHL` (the repair-history record) is not decoded.
- **Restore order is not proven.** Step order comes from `__cstring` order plus the `await_*` pairs. That is strong evidence of grouping, but not a trace. A real restore log (`restored_external` console output) would settle it.
- **Updaters were not disassembled.** Which ones actually run on V68 is inferred from manifest presence and device-tree nodes. The TCON, retimer, PS190, Manta, Banyan, Orion, Peppy, Nitrogen, Madea and Canary steps are assumed to skip on the Duo. `update_ir_mcu` and `update_aht` (`libAHTRestore`, `AHTLoader`) were not identified. The secondary NFC controller (`hammerfest`) has no updater identified.
- **`restored_external` is not in `reference/ramdisk/`.** The repo's ramdisk pages document the upgrade ramdisk only. The erase-ramdisk strings used here were extracted ad hoc and are not checked in.
- **The OTA payload is not examined.** Only the tethered Upgrade identity was. MobileSoftwareUpdate, `mobileactivationd`, the obliteration daemon and System Configuration's client run from the root filesystem or dyld cache, which were not available for this chapter.
- **Some FDR terms are undefined.** The exact meanings of `NonPoR`, `EarlyAccess`, `StoreCombined`, `Lynx` and most four-character data-class tags are inferred from names.
- **Hinge calibration after repair** rests on chapter 08's locationd strings. Whether Apple's repair flow also runs an explicit hinge or IMU calibration step (the manual's "Hinge Issues" page) is not documented in these sources.
- **Erase internals.** The xART wipe is shown by one restored string and MobileKeyBag strings. The SEP side is encrypted, so the key hierarchy that is destroyed is **[PUB]**/**[INF]** only.
- **Public sources are thin.** The Duo repair manual itself (FPZKLK) was not read directly, only press coverage of it.


## [14: Power button to home screen: a cold boot of the Duo, end to end](14-power-button-to-home-screen.md)

### [4. Gaps](14-power-button-to-home-screen.md#4-gaps)

- **Button to power-up.** Which PMU wake source the side button raises from off, what carries the press while the SoC is off, and the rail and reset sequence are not in the sources. The `/buttons` → `smc-pmu` path is only shown for the running OS.
- **Which panel shows the Apple logo**, and whether iBoot reads the fold state at all, are unknown. So is whether the kernel restarts the DCP from FUD or takes over iBoot's running instance.
- **Who starts the IOPs.** iBoot loads most IOP images, but whether it starts the cores or only stages the images for `AppleASCWrapV8`/`RTBuddy` is not stated. The ANS firmware's normal-boot loader and the SMC firmware's source are both unknown.
- **Kernel order.** IOKit matching order between SEP, ANS, AOP, DCP, MTP and GPU is not established; Phase D is grouped, not sequenced.
- **Userland start-up** (launchd, daemon order, data-volume mount, first-unlock and keybag handling before SpringBoard) is not covered by any chapter.
- **Boot pose.** Whether SpringBoard's first pose comes from a live AOP angle or the `SBFDevicePoseLastKnown*` defaults, and how long hinge convergence takes on a cold boot, are not shown.
- **Boot chime.** Which stage plays `Ap,AudioBootChime` was not found.
- **Timing.** No step has a measured time; the trace is ordered, not timed.
- **Verification.** None of this was observed on a running Duo. The vphone-duo runtime results the chapters cite come from a VM.
